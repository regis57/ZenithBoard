# Social sharing

Off by default. Switched on, the Pi posts the aircraft worth a post — a military tanker, a Beluga, a type it has not seen in a month — to **Bluesky**, as a picture with a short text. Two looks for the picture, each beside a map of the aircraft's track, both drawn by the Pi itself in a second or two, on a Pi 3B included, with no browser:

| Look | What it shows |
|---|---|
| `dotmap` (default) | The dot-matrix wall as it is at that moment, and in the right-hand column a map with the aircraft's track over the last minutes |
| `flap` | The split-flap board, beside the same map, wider |
| `alternate` | The two in turn, one post each |

The map can be a plain map, a dark one, satellite, terrain, or none (the track on black, nothing fetched). Until 0.24.0 a third look, `dots`, drew the track in dots in place of a map; it was taken out at the owner's word. A Pi still set to it posts `dotmap`, and the update says so with the command.

```bash
sudo zenithboard social setup      # the Bluesky account, the words, the picture   (or: menu -> 3 Settings -> 6 Social sharing)
sudo zenithboard social test       # draw the picture, print the text, post nothing
sudo zenithboard social on         # from now on, under the rules you chose
```

What it looks like on Bluesky — the author's account, [@zenithboard.bsky.social](https://bsky.app/profile/zenithboard.bsky.social), on 20 October 2026 (0.26.1): a KLM Cityhopper Embraer in the split-flap look on the satellite map, then a Tunisair A320 in the dot-matrix look, each with the photographer's link to Planespotters.

<img src="https://github.com/regis57/ZenithBoard/raw/main/docs/images/social-feed.png" alt="The ZenithBoard account on Bluesky: the profile with its automated-account badge, a split-flap post (KLC70R, Torino to Amsterdam, satellite map), a dot-matrix post (TAR954, Tunis to Brussels)" width="420">

Why Bluesky alone: X closed its free API in February 2026 and charges per post; Threads and Instagram cannot take an uploaded picture, they fetch it from a public address, which would mean putting the Pi on the internet. Bluesky takes the picture directly, costs nothing, and its API is open. Mastodon was supported in 0.18 and taken out in 0.19.0; an update removes its token from the Pi (revoke it on your instance too). See [When a provider changes something](Providers) for the general attitude.

## Step by step

### 1. Create the account, and its app password

The Pi never gets your real password. Bluesky has a secret made for one program, which you can revoke without changing anything else.

Create the account at bsky.app. Then *Settings → Privacy and Security → App Passwords → Add App Password*. Name it `zenithboard`. The password is shown **once**, in the form `xxxx-xxxx-xxxx-xxxx`: copy it. The wizard asks for your handle (`yourname.bsky.social`, without `@`) and that app password.

**Declare the account as automated, before the first post.** This is what keeps an account like this one from being reported and suspended as an undeclared bot: *Settings → Account → Automation label* (*Étiquette d'automatisation*), switch it on (Bluesky 1.119, March 2026). It puts a `bot` self-label on the profile, and a badge shows beside the name on the profile and on every post. Bluesky's developer guidance asks bot accounts to do exactly this.

Say it in the bio as well, in plain words — the badge means nothing to someone who does not know it — and say that the texts are templates, not generated by AI, so nobody has to guess which kind of automated account it is.

Revoking: delete the app password on Bluesky. The Pi's posts stop with the next attempt, and `zenithboard social check` says so.

### 2. Run the wizard

```bash
sudo zenithboard social setup
```

Give the handle and paste the app password (typed blind, as a password); the wizard **tries the account before going further** and stops if Bluesky refuses it. Then it asks for the words:

| Question | What it is for | Default |
|---|---|---|
| Where is this? | The place named at the end of the posts. Your words: a town name (`Trémery`) reads *above Trémery*, words that start with their own preposition (`near Metz`, `over the Moselle`) are kept. The receiver's position is never used. A small village narrows your home down to a few kilometres; a city, a department or a region does not | nothing |
| Sharing radius | An aircraft is a candidate while inside it. Separate from the wall's radius | 15 km |
| Minimum minutes between posts | So the account is not a firehose. Ten at least: a declared bot that posts every minute is what gets reported, so a smaller value is used as ten | 120 |
| Hashtags | Ending every post. Change them any time with `sudo zenithboard social hashtags ADSB avgeek Moselle` — the `#` is optional, and left out the shell cannot take it for a comment; `none` for none at all, `default` for the three | `#ADSB #avgeek #ZenithBoard` |
| What is worth a post | See the rules below | rare, military, helicopter, heavy, farthest |

And then for the picture:

| Question | Choices | Default |
|---|---|---|
| The look | `dotmap` (the dot-matrix wall beside a map), `flap` (the split-flap board beside a map) or `alternate` (the two in turn) | `dotmap` |
| The units, picture and text (0.24.3) | the wall's own, `metric` (m, km/h, km) or `imperial` (ft, knots, mi) | the wall's |
| The colour of the letters and the track | the wall's own colour, or amber, green, red, white, turquoise — the wall's colours, read from its own style sheet | the wall's |
| The map | `normal`, `night`, `satellite`, `terrain`, `none` (the track on black, nothing fetched), `rotate` | `normal` |

**To vary the posts** (optional): the look can be `alternate` — the dot-matrix wall with a map, then the split-flap board, one post each — the colour `rotate` — amber, green, red, white, turquoise in turn, one step per post — and the map `rotate` — normal, night, satellite, terrain in turn: at every post for a fixed look, after each pair of posts when alternating. Five colours against two looks: over ten posts each look meets each colour; over eight, each look meets each map. Since 0.23.0, asked for by the owner, `alternate` is the two looks with a real map. The dark blue went the same day, from the wall and from the posts; a picture colour still set to it gives the wall's colour, and the update says so. `social status` names the next picture. Posts made by hand move the turn on too.

```bash
sudo zenithboard social look alternate
sudo zenithboard social colour rotate
sudo zenithboard social map rotate
```

Each of these has its own command too, for a quick change: `social words`, `social picture` (the three picture questions), `social look dotmap|flap|alternate`, `social colour green|wall`, `social units imperial|wall`, `social photolink on|off`, `social map satellite`.

### 3. Try it

```bash
sudo zenithboard social test
```

Waits up to half a minute for an aircraft with a track, draws the picture, and prints the text and the alt text. **Nothing is posted, ever, by `test`.** It always finds something to show (it adds the `all` rule for itself), so it also says plainly whether the service, under *your* rules, would post that aircraft — and if not, why not. The picture is at `http://PI-ADDRESS:8080/social/preview`, on your home network like the wall. `social test 4071f1` does it for one aircraft by its hex code.

**Post now** (menu, or `sudo zenithboard social post`) is different: it posts the aircraft it finds at once, whatever the rules and the gap. Use it to see a real post; the service itself waits for an aircraft your rules pick. A post made by hand counts for the service like its own: a gap, if you set one, starts again from it, and that aircraft is not posted again during the same crossing.

### 4. Switch it on

```bash
sudo zenithboard social on
zenithboard social status
zenithboard logs social
```

`on` installs what the picture needs from Debian if it is missing — Node (about 30 MB; it draws the dot-matrix picture and formats the rows of both), plus Pillow with the DejaVu fonts for the two looks with a map, `dotmap` and `flap` (a few MB) — starts the service, and says the rules it will follow. `off` stops it and keeps the account; `remove` forgets the account too.

## The words (0.29.0)

`sudo zenithboard social sentence ...` (menu *Social sharing → 6*) chooses the shape of a post's text. Templates, filled from the flight's own data — the account says "Texts from templates, not AI" and that stays true. On RYR5ZK, Brussels → Pisa, above Trémery:

| Shape | The post |
|---|---|
| `factual` (default) | Flight Ryanair #RYR5ZK · Boeing 737-800 · Brussels → Pisa · altitude 10 570 m · above Trémery |
| `story` | A Ryanair Boeing 737-800 bound for Pisa from Brussels has just crossed the sky above Trémery, 10 570 m up. #RYR5ZK |
| `board` | ✈ #RYR5ZK · EI-ENK / Brussels → Pisa / Boeing 737-800 · 10 570 m · 720 km/h / Above Trémery at 20:37 (four lines) |
| `spotter` | EI-ENK, a Ryanair Boeing 737-800, flying Brussels → Pisa as #RYR5ZK: 10 570 m above Trémery at 720 km/h. |
| `lookup` | Look up, Trémery! Ryanair #RYR5ZK is passing 10.6 km overhead on its way from Brussels to Pisa. |

Several shapes, comma-separated (`story,spotter,lookup`), or `random`: one is drawn at each post. The reason the post was made comes first when the words do not already say it: `Rare visitor:`, `Heavy overhead:`, `Military traffic:`, `Helicopter:`. A range record keeps the factual words, which say "range record for 30 days" and where it was seen from rather than "overhead". A shape that lacks what it needs (an aircraft with neither airline nor type) or would pass 220 characters gives the factual text, which can be cut cleanly at Bluesky's 300. No shape ever says the distance or the direction from the receiver: with the area, they would place it. The hashtags, the map's credit and the photo link follow as before.

## The week's summary (0.33.0, optional)

`sudo zenithboard social weekly on` (menu *Social sharing → 7*, off by default): on Sundays from 19:00 the service posts the seven days ending that day, from the [statistics](Statistics) — so statistics must be on. The text:

> The week above Trémery, 12–18 October: 3 587 aircraft heard, 58.7 million messages decoded.
> Busiest day: Monday, 612 aircraft. Busiest hour: 13:00.
> Most seen: Ryanair (2 144), easyJet (1 171), Lufthansa (762).
> Top type: Airbus A320.
> Posted here: 41 crossings.
> #ADSB #avgeek #ZenithBoard

The lines after the first are dropped from the end when the hashtags would not fit in Bluesky's 300 characters; the first always stays. The picture is drawn by the Pi (Pillow, 1200 × 675) in the posts' colour: the counts, the week by hour (a dot per hour, brighter where more aircraft had a position, as on the statistics page) and the airlines most seen as bars, with their names in plain text — no logos.

![The weekly summary card (a preview, made-up figures)](https://raw.githubusercontent.com/regis57/ZenithBoard/main/docs/images/social-weekly.png)

**What it never says**: a distance, a direction, a range. The farthest aircraft of the week is left out on purpose: named with the city nearest it, two such posts would narrow down where the antenna is. Only your own words for the place (the area of the wizard) say where.

Once a week (the ISO week): a Pi switched off on Sunday evening posts nothing on Monday, a summary a day late not being what the account promises. A post that fails waits ten minutes like any other; a week with no statistics is skipped, said once in the journal (`zenithboard logs social`). `sudo zenithboard social weekly test` draws this week's so far and prints the text, posting nothing (see it at `/social/preview`); `social weekly post` posts it now, and Sunday's still goes out. The airlines and the type come from the fleet lists of 0.31.0; the crossings posted are counted from 0.33.0.

### Dot-matrix with a map

![The dot-matrix picture with a map: RYR5236, Pisa to Brussels, over Metz, a real post of 20 October 2026](https://github.com/regis57/ZenithBoard/raw/main/docs/images/social-dotmap.jpg)

The wall's rows as the tablet shows them (`FLT  EWG11S`, `REG  D-AIDO`, then airline, type, altitude, speed, route), with two differences: the time on the last row with its offset from GMT as the Pi's time zone has it that day (`11:39 GMT+2` in a French summer, `GMT+1` in winter), where the tablet shows the distance and direction; and, in the right-hand column, a map where the tablet has the silhouette and the photo. The flags are the wall's: the country of the registration beside the `REG` row (since 0.20.0; it sat beside the airline, where it read as the airline's country), and the maker's beside the model.

`sudo zenithboard social look dotmap` (0.23.0, asked for by the owner; the default since 0.24.0): the map is the split-flap look's, below — the same four maps, the same credit, the same `social map` setting and its `rotate` — with the track, the aircraft, the key and north. Node draws the dots with that column left dark and says where it is; Pillow lays the map there and writes a JPEG under Bluesky's limit. The map is a strip 400 pixels wide and 800 high, so when the aircraft would land under the key, the view is chosen in the part above the key and the credit: an aircraft flying south ends above the key, not under it. With `social map none` the strip shows the track on black over a faint grid, and nothing is fetched.

*Above: a real post from the reference Pi, 20 October 2026 (0.27.3), with the light map: RYR5236, Pisa to Brussels, over Metz. Twenty-six names from the region's own list (`social places on`), Pont-à-Mousson, Nomeny and Rémilly filling the south of the map. When the tiles do not come, the strip shows the track on a dark grid, with no credit.*

**Town names (0.24.4).** On the satellite and terrain maps EOX's label layer named one village in forty kilometres (Amnéville, on a real post over Metz). ZenithBoard now names the towns itself: the places of 5 000 inhabitants or more from a list it ships (`flightinfo/data/places5000.tsv.gz`, GeoNames, CC BY 4.0, made by `tools/make_places.py`), the largest first, at most twenty-six in a smaller type (0.25.2; sixteen before); a map with fewer than three of them takes the villages of 1 000 to 4 999 too (0.26.2, `places1000.tsv.gz`, read only then: DAH1217, two minutes after leaving Metz-Nancy, went out on a strip east of the Moselle with no name at all), never over another name, the aircraft, north or the key, and drawn over the track so that it never cuts a letter out of a town (0.25.3; each dot stays where its town is). Nothing is looked up for it. Since 0.25.3 the `normal` and `night` maps carry the same names. **No town is named twice (0.26.1):** in 0.25.3 those two maps were EOX's OpenStreetMap layer, whose own labels stayed under ours, a few pixels apart (EWG8QR over Nancy, on a real post). EOX has no OpenStreetMap layer without labels, so these two maps are now built from two EOX layers that carry no name, the light relief (`terrain-light`) and the roads (`streets`, white, tinted orange for the light map), and every map ZenithBoard names is drawn on such layers only (a test holds it). The price: the main roads only, not OpenStreetMap's small ones. **The scale is the map's own:** the bar is worked out from the zoom and the latitude (Web Mercator, 156 543 m per pixel at zoom 0 on the equator), so the track, the bar and the distances between towns agree: Metz to Thionville, 28 km, measures 27 km against the bar on a preview.

**Town names anywhere in the world (0.27.0).** The shipped lists name the places whose population GeoNames knows, and GeoNames knows it unevenly: 2 074 places of 5 000 or more in France, 479 in Indonesia, a country four times as populous, where 257 515 of 258 055 populated places have no population at all. On test maps the shipped lists named nothing over East Sumba, one place around Pontianak (Borneo) or Ulaanbaatar. `sudo zenithboard social places on` (menu *Social sharing → 5*) makes the region's own list on the Pi: it downloads GeoNames' file of every country with a place of 500 or more within 400 km (download.geonames.org, CC BY 4.0; 24 MB around Metz since 0.27.2, 10 MB for Java, once), keeps every populated place within 400 km and gives each a weight, its population when known, otherwise its rank: national capital, province seat, district seat (PPLA2: 50 000), subdistrict seat (PPLA3: 10 000), village seat (PPLA4: 2 000), village (100). Parts of a town, historical and abandoned places are left out, and a lighter place within 1.5 km of a heavier one is taken for a part of it. The maps then name the heaviest first, down the same tiers as the shipped lists: 5 000 and more, then 1 000, then any place, until three are named. **Then the empty parts (0.27.3):** the heaviest village wherever no name is within 120 pixels of it, so that seven towns on the edges of a map (SWR3AG over the Moselle plateau) no longer leave the 30 km between them bare. **Along the track (0.28.0):** all of this within 70 pixels of the aircraft's track, plus three of the largest cities elsewhere on the map (50 000 or more, 150 pixels apart) to say where the map is; the rest of the map only when the track's surroundings give fewer than three names. RYR5ZK, Brussels → Pisa, had a dozen towns in the north of its map and few along a track from Namur to Luxembourg; it now names Namur, Ciney, Rochefort, Bastogne, Arlon, Luxembourg, Hayange and Metz along the line, and Leuven, Aachen and Trier around it. The list stays on the Pi (a few hundred kilobytes, readable by the service only since 0.27.1: its first lines give the centre, the receiver's position); nothing about the receiver is sent, the country files being the same for everyone. Beyond 400 km (a farthest aircraft), the shipped lists are used.

Measured with the real code, GeoNames' real files and EOX's real tiles, on 20 October 2026, a light map 420 by 840 pixels, a 2-minute track (the most zoomed) and an 8-minute one, names shown with the shipped lists → with the region's list: East Sumba 0 → 11 and 0 → 3, Pontianak 0 → 19 and 0 → 10, Ulaanbaatar 0 → 7 and 3 → 12, Kano 1 → 6 and 12 → 24, Manaus 2 → 11, Yellowknife 0 → 2 and 0 → 7, Lima 8 → 24 on the 8-minute map; Trémery 8 → 9 and 26 → 26, Jakarta and Nairobi about the same. One fewer: Innsbruck on the 2-minute map, 11 → 4, because the shipped list counts the city's districts (Arzl, Pradl) as places of their own and the region's list does not; the map stops at three towns, as everywhere. A name now goes left of its dot when the right is taken, and a place is never named twice.
| `none` | No map: the track on black, over a faint grid. Nothing is fetched | none | none |

**Where the map comes from, and why there.** The tiles come from [EOX::Maps](https://maps.eox.at), whose layers are free to use with attribution and a link back. The whole required text is drawn on the picture and read in its alt text; the post ends with one short line whose names are links — *Map © OpenStreetMap, EOX* — which is what OpenStreetMap's [attribution guideline](https://osmfoundation.org/wiki/Attribution) accepts (the name, linked to its copyright page) and what EOX asks of an online publication (the name and the link). Until 0.19.6 the post repeated the whole text, three lines of small print under every aircraft. OpenStreetMap's own tile servers are not used: their [usage policy](https://operations.osmfoundation.org/policies/tiles/) rules out automated fetching that nobody is looking at, which is what a service posting by itself does. The satellite layer is licensed CC BY-NC-SA 4.0: free for a hobby account like this one, **not for commercial use**, and a picture made with it is shared under the same licence. The Pi asks only for the few tiles under the picture, names itself in every request, and keeps them for a month under its state folder, so the tiles over your area are fetched once, not at every post. If the tile service does not answer, the picture is drawn with no map and no credit, and `social test` says so.

### A link to the aircraft's photo (0.25.0, optional)

`sudo zenithboard social photolink on` (or menu *Social sharing → 4*): when the wall has a Planespotters photo of the aircraft, the post ends with a line *Photo: Jane Doe / Planespotters*, the whole line a link to the photo's page. The photographer is named and the picture opens at Planespotters, full size. **Only the link**: Planespotters' [photo API terms](https://www.planespotters.net/photo/api) forbid storing, re-hosting or passing on the picture, so it is never posted, and the post carries no link card (Bluesky's card would mean uploading the thumbnail). With photos off on the wall, or no photo for that aircraft, there is no line. When the text would not fit beside it, the line is left out rather than the text cut. JetPhotos is not used: it has no photo API, and finding out whether it has a photo would mean querying the site, which its terms do not grant. Off by default.

## What gets posted, and what never does

**The rules.** An aircraft is a candidate while inside the sharing radius (except a range record, below), known (a type, a registration or an airline — an aircraft with nothing known is never posted), airborne, with at least thirty seconds of track, and not already posted during this crossing (below). Among the candidates, the rules say which are worth it:

| Rule | Posts an aircraft that is… |
|---|---|
| `rare` | of a type that at most two *other* aircraft have flown in the last thirty days. Counted per aircraft, not per look |
| `military` | military, by the decoder's database flag or by its type |
| `helicopter` | a helicopter |
| `heavy` | an A380, 747, Beluga, Antonov 124/225, C-5, C-17, A400M, or any four-engined airliner |
| `farthest` | a new range record: farther than anything in the last thirty days, and over 50 km. Looked for in the whole sky, not only inside the sharing radius |
| `all` | everything that flies over, the special aircraft included: ticking `all` is ticking every line. When several are there at once, the special one goes first, then the others. (Called `any` before 0.19.1; the old word still works) |

`rare` and `farthest` judge against history, so they wait until the service has watched for **three days**; `zenithboard social status` says where it stands. The other rules work from the first minute.

Several rules can match; the best candidate is the one matching the most, and knowing the most (route, airline, model each count); between equals, the one that came inside the radius first. One post at a time, and the next as soon as the last is out.

**One post per crossing, every crossing (0.20.0).** A crossing starts when an aircraft comes inside the sharing radius and ends when it has been outside it for an hour. Whatever it does in between — circling, or leaving and coming back in five minutes later — it is posted once. The same airframe back after that is another crossing and is posted again: the return flight in the evening, the same rotation the next day. A new callsign is another flight even sooner (an aircraft turned round at a nearby airport, leaving under another number); a callsign that only appears or disappears on the way is not. An aircraft that left the radius before its turn — its route still being looked up, another one posted first — is still posted, up to ten minutes after it left, with what the wall shows of it then: every crossing counts, not only those caught at the right moment.

**Nothing caps the posts.** By default there is no gap between two posts: the feed is the sky over your radius, each aircraft once per crossing, as many as there are. The radius is the control: five times the radius is twenty-five times the area, and roughly that many more crossings. Bluesky's own ceiling is far above what one receiver's sky can give: 1,666 posts an hour. A gap can still be set (`sudo zenithboard social gap 30`, or in `social words`; `social gap 0` for none); from 0.19.3 to 0.19.10 it could not go under ten minutes, which is gone.

**Complete before posted.** The wall looks up an aircraft's route and, when the decoder does not know them, its registration and model on adsbdb.com, and it does so when the aircraft comes inside the radius it is asked about — the sharing radius, for the service. Those answers take a few seconds — longer when adsbdb's route is for another flight under the same callsign, which the wall refuses, and hexdb.io is asked for a second opinion (since 0.19.9 that second answer is waited for too: two flights went out without a route that hexdb had a few seconds later). An aircraft whose lookups are still on their way waits, up to two minutes from the moment the service first saw it waiting; then it goes with what is known. (Before 0.19.5 it went at once: a KLM flight was posted with empty registration, model and route rows, because its track, followed from far out, was already long enough.) `social test` waits within its own half minute, then shows what is known.

**The text.** Says what the wall knows, in English, and nothing it does not. It starts with the flight and ends with the place you gave (here `Trémery`); the altitude is said as one (*altitude 8 500 m*) so it never reads as a distance from the place; an airline callsign is a hashtag, so the flight can be followed:

| Case | Text |
|---|---|
| Airline flight, route known | `Flight Etihad #ETD11K · Airbus A380-800 · Paris → Abu Dhabi · altitude 8 500 m · above Trémery` |
| Airline flight, route unknown | `Flight British Airways #BAW123 · Airbus A380-800 · altitude 11 900 m · above Trémery` |
| Callsign, no airline known | `Flight #BGA113J · Airbus A330-743 Beluga XL · F-GXLH · altitude 9 750 m · above Trémery` |
| Registration only | `Aircraft D-EABC · Cessna 172 · altitude 910 m · above Trémery` |
| Helicopter | `Helicopter D-HABC · Airbus Helicopters H145 · altitude 460 m · above Trémery` |
| Military | `Military flight #RCH123 · Boeing KC-135R Stratotanker · altitude 7 620 m · above Trémery` |
| Range record | `Flight Emirates #UAE201 · Boeing 777-300ER · … · altitude 11 280 m · range record for 30 days: over 300 km out, seen from Trémery` |
| Nothing known | no post |

The registration is said when no airline is: an airline flight is known by its callsign, and the registration is on the picture. A range record ends with *seen from* rather than *above*: it was nowhere near overhead. Then the hashtags (`#ADSB #avgeek #ZenithBoard` by default, `sudo zenithboard social hashtags …` to change them; `#helicopter` or `#military` replace `#avgeek` when they apply, or are added when `#avgeek` is not there, unless the hashtags are `none`), and last, when the picture has a map, its credit in one short line. The picture carries an alt text built from the same facts, for screen readers, with the map's full credit. Units follow the wall's setting.

**What never leaves the Pi:**

* **The receiver's position**, and anything that gives it away: the posts carry no bearing and no distance — a range record says *over 300 km*, rounded down to 50, which tells the record and draws no useful circle — the picture's last row shows the time where the tablet shows `12KM NE`, and the track, on dots or on a map, is centred on the aircraft with nothing marking the receiver. A hundred posts give nothing to triangulate. The map's tiles are asked for by the Pi, from your connection, like any map you would open.
* **The Planespotters photo.** Their terms forbid re-hosting it. The track takes its place.
* **The secret.** It lives in `/etc/zenithboard/social.env`, owned by root, readable by the `zenithboard` group (the service's user), mode 0640; never in `config.env`, never in a log, never in `zenithboard config`. `zenithboard security` checks the file's owner and mode.
* **The picture itself**, after the post: it is drawn in `/run/zenithboard/social` — memory, not the card — and deleted once Bluesky has answered, whether it took it or not.

## How it works

`zenithboard-social.service` runs `flightinfo/social.py` as the `zenithboard` user inside the same sandbox as the wall (exposure at most 1.5 on systemd's scale; `tests/test_units.sh` holds the ceiling). Every five seconds it reads the decoder's `aircraft.json` and keeps the last fifteen minutes of positions per aircraft in memory. Every fifteen seconds it asks the wall itself, on the loopback, which aircraft are inside the sharing radius — with everything the wall knows about them: airline, model, route, flags. When a candidate passes the rules (and a gap, if one is set, has passed), it draws the picture and posts it, then looks again five seconds later rather than fifteen, in case another is waiting its turn. It also notes, from the decoder's positions every five seconds, which aircraft are inside the radius: that is what keeps a crossing going, even at a moment the wall does not answer.

The dot-matrix picture is `tools/social-render.js`: Node reads `app.js` and lifts the wall's own text functions (the way the tests do), draws the rows and the flags from `flags.js`, and writes a PNG with Node's `zlib`; the colours come from the wall's `style.css`. The right-hand column starts at dot 88, two dots clear of the flags (dots 74 to 86 with an outline): until 0.23.0 it started at 86 and its frame was drawn over a German flag's outline. The script leaves that column dark and says where it is in pixels; `social_card.py` lays the map there (`render_dotmap`) and writes a JPEG, like the split-flap picture. The split-flap picture asks the same script for the board's rows (`--lines`, the wall's own formatting) and paints them with Pillow in `flightinfo/social_card.py`, with the map tiles and the track; a JPEG of about 500 KB, under Bluesky's limit of 1,000,000 bytes (the quality steps down if a picture would not be). A Pi without Pillow (installed by `social on`, `social look` and `social test`, so only an offline Pi) gets the dot picture with the track drawn in dots in that column, as `dots` drew it before 0.24.0, rather than no picture; the service's journal says why.

Bluesky is the standard library only: a sign-in (`createSession`), then for each post `uploadBlob → createRecord`, with the hashtags and the map's link as facets so they are clickable, and the alt text and the aspect ratio with the image. **The session is kept**, in memory only: Bluesky allows an account [300 sign-ins a day and 30 in five minutes](https://docs.bsky.app/docs/advanced-guides/rate-limits), and signing in for every post, as 0.19 did, would pass that on a busy day once every crossing is posted. After an hour the access token is renewed with the refresh token (`refreshSession`); a new sign-in only if Bluesky refuses it, or if the account in the file has changed. A token refused in the middle of a post means one new sign-in and one more try, never a loop. `social check` always signs in afresh: that is what it is for.

State lives in `/var/lib/zenithboard/social/state.json`: for each type, the last few distinct aircraft seen and the day (for `rare`), the farthest aircraft of each of the last thirty days (for `farthest`), the day the service started watching, the aircraft posted whose crossing is not over yet (each with the callsign it was posted under; the 0.19 form, a bare time, is read too), the times of the last day's posts, and the last post's time. The map tiles are cached next to it, in `tiles/`, at most 60 MB and a month. Once an hour the service writes one line to its journal — how many looks, how many found a candidate, when the next post is possible — so `zenithboard logs social` answers *why no post?* Its first line says which version it runs. **Memory:** the service measures its own — about 40 MB at rest, up to about 140 MB in the second it draws a split-flap picture (Python with Pillow, plus Node for the rows) — and gives the figures in its hourly journal line and in `sudo zenithboard social status`. `systemctl status` cannot: Raspberry Pi OS boots with the kernel's memory controller off (`cgroup_disable=memory`), so systemd shows no *Memory* line, and the unit's `MemoryMax=300M` only takes effect on systems where that controller is on. ZenithBoard does not change the boot command line for it. `social remove` deletes it all.

## Updating and removing

`sudo zenithboard update` carries the service like every other: the unit file is refreshed and the service restarted when sharing is on. The secret is untouched by an update — except a Mastodon token left from 0.18, which the update removes.

```bash
sudo zenithboard social off       # stop posting; account kept
sudo zenithboard social remove    # account, state, map tiles and service gone (Node and Pillow stay: apt remove nodejs python3-pil)
```

## Troubleshooting

| What you see | What to do |
|---|---|
| `social status` says it *cannot read* the account file or the state folder | You ran it as `pi`. Those files belong to the service's user; `sudo zenithboard social status` reads them as that user |
| `social status` says the service *runs the code from before the last update* | `sudo systemctl restart zenithboard-social`. Since 0.19.3 an update restarts it by itself; before, it only made sure it was enabled, and a running service kept its old code |
| `social check` says FAILED | The handle has no `@`, and the password is the *app* password, not the account's. Make a new app password if in doubt |
| `social test` says nothing to show | No aircraft with thirty seconds of track inside the sharing radius right now. Try a wider radius, or `social test HEX` with an aircraft from `zenithboard status` |
| It posts nothing | First: `test` never posts. Then `zenithboard social status` — is it *on*, is the account ready, is a gap set and still running? Does it say the aircraft you expected is in a crossing already posted? Then `zenithboard logs social`: the hourly line says how many looks found a candidate. `rare` and `farthest` start after three days, so on the first days only `military`, `helicopter` and `heavy` can fire: tick `all` to see it post the ordinary traffic too (the special aircraft still go first) |
| A post went out, but not by the service | *Post now* posts at once, whatever the rules. The service's own posts show in `zenithboard logs social` as `posted …` |
| The split-flap picture has no map | The Pi could not reach `tiles.maps.eox.at` (no internet, or the service busy: EOX limits heavy load). `social test` says so; the next picture tries again. `social map none` stops asking |
| `zenithboard logs social` shows `the wall did not answer` | The wall server is down: `zenithboard status`, `zenithboard logs flightinfo` |
| A post went out that you would rather not have | Delete it on Bluesky. Narrow the rules with `social words`. Nothing posted can be recalled by the Pi |
